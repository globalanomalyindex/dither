# DITHER Decision Log

| ID | Decision | Status | Rationale | Consequence |
|---|---|---|---|---|
| DEC-001 | Use Exposed Logic first and SIGNAL//BODY v2 as the visual and interaction review standard. | Accepted | These frameworks preserve authored expression while making mechanisms and state legible. | Visual polish remains subordinate to task clarity, accessibility, and truthful system behavior. |
| DEC-002 | Preserve DITHER's workshop character instead of replacing it with a generic SaaS design system. | Accepted | The product already has a distinct thesis tied to image transformation. | Signature elements are tested for purpose and hierarchy, not removed by default. |
| DEC-003 | Keep a static, client-side runtime while allowing a professional development toolchain. | Accepted | This retains privacy and deployability while enabling testing, CI, linting, and reproducible builds. | Node is a development requirement, not a shipped runtime requirement. |
| DEC-004 | Use selective TypeScript and module boundaries rather than a full rewrite. | Accepted | The highest-value boundaries are state, commands, document modeling, workers, and testable utilities. | Legacy engines remain in place until protected and worth extracting. |
| DEC-005 | Treat algorithm output fidelity as protected product behavior. | Accepted | DITHER is a creative processing tool, so silent pixel changes are product regressions. | Golden fixtures and invariants precede deep engine changes. |
| DEC-006 | Make the product a real creative tool first and an inspectable portfolio artifact second. | Accepted | Portfolio credibility should emerge from product quality and evidence, not staged presentation. | Repository and case study expose decisions, tradeoffs, tests, and limitations around the working product. |
| DEC-007 | Preserve Dither, Grain, and Paint as recognizable capabilities within one document and history model. | Accepted | Separate personalities help orientation, but separate products fragment the workflow. | Later plans share viewport, checkpoint, comparison, and export concepts across capabilities. |
| DEC-008 | Use progressive expert disclosure rather than removing advanced controls. | Accepted | The depth is valuable, but the baseline presentation requires too much scanning. | Stage selection and inspector context determine which controls are visible. |
| DEC-009 | Use Figma only for spatial decisions that are materially clearer as editable comparisons. | Accepted | Code remains the source of truth for behavior and feasibility. | Figma is not required for every screen or component. |
| DEC-010 | Use editable SVG for interface icons. | Accepted | Icons must remain inspectable, scalable, themeable, and accessible. | Generated raster icons are excluded from product UI. |
| DEC-011 | Use generated imagery only for a project-owned sample or non-evidentiary case-study art with provenance. | Accepted | Generated media cannot substitute for real product evidence. | Screenshots, test output, and before and after comparisons remain authentic. |
